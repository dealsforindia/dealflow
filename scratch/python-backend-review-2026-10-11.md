## System as implemented

Telegram ingestion is implemented twice: `listener.py` receives channel events and LPUSHes `queue:deals`; `bot.py` also retains its own scraper/process loop and handles approval broadcasts. `worker.py` consumes Redis, resolves merchant links, enriches and scores offers, writes `UniqueDeals`, emits events and can dispatch GitHub video workflows. DesiDime is a separate scrape/format/publication pipeline. AJIO, Amazon and D2C harvesters provide additional acquisition paths.

FastAPI `api.py` provides private curation endpoints and public directory/search/history/review/outbound endpoints. It forwards several Redis channels to `/ws`. MongoDB stores deals, settings, alerts and multiple forms of price history; Redis carries queues, pub/sub and caches. IndiaDealHunts consumes public data; DealFlow controls curation. `oos_expiry_worker.py` runs the separate merchant-price/stock sweep. A second expiry loop remains inside `worker.py`.

`commerce_engine_v2` is a separate, more conservative pipeline with product/variant context, verification status, discovery-only caching, and SQLite observation history. Its existence does not mean the active FastAPI API uses it. No import wiring from the reviewed active backend to `CommerceEngine` was found. Repricing and SMT solver modules similarly have standalone examples but no active-backend callers found.

## Findings with source evidence

“Deployed source” means the reviewed VM file contains the defect; it does not substitute for reproducing its effect in the running process.

1. **High — Redis consumer can starve the worker event loop.** `worker.py:2721` uses synchronous `_redis.blpop(..., timeout=5)` inside `async def worker_loop`. The normal empty-queue path immediately continues, and the populated path calls `asyncio.create_task` without awaiting/yielding. Neither path gives the event loop a chance to run the scheduled processors or background tasks. A semaphore inside those tasks does not resolve this. PM2 `describe worker` confirms the worker script path is `/home/rudranil777/dealbot/worker.py`. Disk source matches local. Fix requires an async Redis consumer and bounded task ownership/backpressure, plus delivery acknowledgement/recovery rather than popping work before success.

2. **High — Two API history routes fabricate observations.** `api.py:4274–4289` creates random historical prices when observations are absent, then returns `has_price_history` and `is_lowest_price`. Separately, `api.py:6458–6473` inserts MRP (or reverse-computed reference price) at a fictional timestamp seven days earlier and labels the result verified at `6491`. Deployed source. These must be removed independently; an attractive chart cannot replace missing evidence.

3. **High — Public feed can falsely claim an all-time low.** `deal_velocity_engine.py:310–318` uses `[mrp, current_price]` as historical data when real observations are missing. `api.py:1765` calls this engine, and `api.py:1795` uses its result for the public lowest-price flag. The feed Mongo projection at `1324–1388` does not include `price_history`, so this consumer loses stored history before computing price position. Deployed source. Project actual observations and return unknown when insufficient history exists.

4. **High — Scanner price events do not reach the storefront.** Scanner publishes `deals:price_update` (VM `oos_expiry_worker.py:272`; local `253`), while the API WebSocket subscribes only to finalized/new/approved/status channels at `api.py:472`. The local storefront hook also has no `price_update` branch. New-deal updates and price updates are separate paths; fixing one does not fix the other.

5. **High — Drip queue consumer is defined but not started.** `api.py:488–501` defines `broadcast_queue_worker`; startup at `504–506` only starts `pubsub_listener`. No other call site was found. VM-only `broadcast_queue.py` enqueues and marks deals queued, but without a consumer automatic scheduled publication will not run. Deployed source.

6. **High — Duplicate route/function definitions produce conflicting behavior.** The full duplicate inventory lists eight repeated names in `api.py` and one in `worker.py`. Direct proof: batch video dispatch at `api.py:7257` resolves the later `dispatch_deal_video` definition at `7881`, which merely sets `ready_to_dispatch`, overriding the original implementation at `7097`. Identical delete/unpublish routes occur at `4882/5096` and `4863/5137`; the later implementations contain cache invalidation and Redis publication absent in the earlier registered handlers. Python name replacement and FastAPI route registration are different mechanisms; the last function definition does not replace an earlier route handler. Consolidate deliberately, preserving intended admin functionality.

7. **High — Stock verification sometimes labels unknown data as verified.** VM-only `stock_verifier.py` returns `verified=True` for unknown Amazon/Flipkart pages, returns Myntra in stock even without a price (`True if price_val else True`), and generic pages in stock solely because no OOS phrase matched. Conversely, missing Amazon/Flipkart prices can become `in_stock=False`. Merchant block pages, recommendation products and availability of other variants require an explicit unknown state. The separate scanner has a success guard; that guard does not repair this alternate verifier.

8. **High — Alerts are consumed without confirmed delivery.** Local `oos_expiry_worker.py:306–308` (VM `325–327`) constructs a Telegram Request but never sends it. Both deal-trigger and radar paths mark alerts triggered even when sending fails; `email_service.py:264` returns `success=True` for simulated/failed SMTP delivery. A Telegram handle also satisfies the email path's broad `"@" in contact` test. The changed VM scanner's deal-trigger branch was read directly and contains the same defect. Keep failed notifications retryable and validate contact type explicitly.

9. **Medium — Alert matching can match the wrong product.** Local `oos_expiry_worker.py:286` (VM `305`) compares URLs by substring, and falls back to title containment. With an empty deal URL, `url in al_url` is true for every nonempty subscriber URL; variant URLs can also overlap. Use the same merchant/product/variant key used by price history. Both local and deployed branches were confirmed.

10. **Medium — Alert email savings can be invented.** `api.py:3323` sends `original_price=float(curr_price) * 1.15` on immediate alerts. That is an assumed 15% higher reference, not a recorded previous price. The API also accepts a client-supplied `current_price` and may trigger from it. Deployed source.

11. **Medium — Coupon magnitude is inferred from code digits.** `coupon_extractor.py:114–121` and `151–158` infer 5–90 as percent and larger digits as fixed currency. `FLAT50` alone does not prove 50% rather than ₹50 or an eligibility condition. Keep an extracted code separate from a verified discount amount and checkout estimate. Deployed source.

12. **Medium — Ratings and review counts have weaker evidence paths.** The dedicated `public_reviews.py` enforces product identity and preserves unavailable/blocked states. In contrast, `store_scraper.py:649` takes the first page-wide star match, and `654–667` conflates rating/review counts. The public feed also substitutes the counts for each other (`api.py:1841–1842`). Recommendation stars or rating totals can therefore be represented as product customer-review evidence. Deployed source. Use the strict review collector consistently and preserve distinct totals.

13. **Medium — “Verified” badges do not establish verification.** `deal_intelligence.py:530–537` awards Store Verified from an image/ASIN and Coupon Active from a sufficiently long coupon string. `heat_score.py:107` labels low-scoring deals Verified Deal. `universal_store_engine.py:518` falls back to Verified Store when identity is unresolved. These are heuristic/default labels, not evidence of current price, coupon eligibility or store identity. Deployed source.

14. **Medium — Arbitrage profit is an estimate presented as guaranteed.** `arbitrage_engine.py:25–102` contains fixed buyback values without a live quote, capacity/condition/eligibility or fees. `155–210` subtracts purchase price and generates profit instructions. Worker consumes it at `2317–2318`, and the API exposes arbitrage data at `1834–1835`. Deployed source. Preserve the feature but label estimates and require a dated, applicable quote before making guarantee claims.

15. **Medium — Analyzer's live event goes to an unsubscribed channel.** `deal_analyzer.py:285` publishes `deals:frontend`; API subscriptions at `api.py:472` exclude it. The analyzer also permits original deal prices when live scraping fails (`deal_analyzer.py:184–190`), while labeling accepted output verified. Admin endpoint at `api.py:4902` can invoke it. Deployed source.

16. **Medium — Price and stock extraction can come from unrelated elements.** Amazon parser at `store_scraper.py:494–517` accepts page-wide price regexes before product-bound buy-box evidence. Default stock begins true even with no HTML. Scanner consumes this scraper; the strict public-price parser does not protect that ingestion/scanning route. Deployed source. This is a concrete extraction risk; specific observed price reversals still require per-product/variant captures to establish which values were wrong.

17. **Medium — Price-history schemas and keys are inconsistent.** Local `backfill_price_history.py:44–50` writes `price`; deployed `price_history_tracker.py` reads only `sale_price` in its intelligence aggregation. The API history route tolerates both, but the tracker does not. Product-key formats also differ (`amz:`, `amazon:`, `fk:`, URL/title keys). Backfills can succeed yet remain invisible to another reader, and Flipkart variant PID is not consistently retained. Do not mass-migrate without an explicit canonical schema and backup.

18. **Medium — Listener configuration refresh creates Mongo clients repeatedly.** `listener.py:243` creates a new `AsyncIOMotorClient` on each refresh, without closing/reusing it. It refreshes pause flags but does not rebuild the startup event subscription for newly added channels. Shared channel ID mappings also disagree for Technical Sheikh and Trending Loot Deals between `listener.py` and `channel_aliases.py`. Deployed source. Verify intended peer IDs with existing Telegram dialogs before changing mappings.

19. **Medium — Public pagination mixes raw offsets with filtered counts.** `api.py:1322` counts raw Mongo matches, then fetches/filters/deduplicates a larger window, limits returned offers at `1438`, and calculates has_more from sanitized length at `1878`. If a window contains rejected/duplicate offers, advancing by the displayed count can overlap windows or leave has_more true on empty pages. Ranking only within each fetched window also cannot establish global intelligence/heat ordering. Deployed source.

20. **Medium — Genie fallback manufactures MRP.** `genie_history.py:178` substitutes `regularPrice * 1.3` when merchant MRP is absent. Its lookup fallback can use the last historical value as current price (`45–53`), default stock true and default worth scores. The Google Shopping wrapper intentionally ignores these current-price/stock/score defaults, which is good, but other consumers must not present them as merchant evidence. Deployed source.

## Non-bugs and remaining checks

- The VM inventory is readable, and matching core disk hashes give strong evidence these source issues are present in deployment. Some Python processes may still have older versions loaded; establish runtime version/start times before attributing every behavior to disk contents.
- Google Shopping results are explicitly unconfirmed listings in the reviewed wrapper. They are not inherently fake merely because they are not in the curated feed.
- `public_reviews.py` does not seed default stars. It may legitimately return blocked/unavailable when a merchant refuses automated access; availability across all three stores needs merchant-specific runtime evidence.
- Repricer/SMT/fake-MRP demo claims exceed their current integration and evidence. No active caller was found for the standalone repricer and SMT solver; do not advertise them as working storefront capabilities.
- Tests and repair scripts were read, not executed. Several mutate databases, delete records, send Telegram posts or deploy code. Running all `.py` files would not be a valid read-only review.
- PM2 online status and a green API health endpoint do not prove worker queue progress, alert delivery, historical evidence correctness or publication completion.

## Recommended order, without changing DealFlow features

Repair worker scheduling/backpressure and start the queue consumer first. Remove all invented historical/reference data and unsupported verification claims. Define one public event schema and product/variant identity model across ingestion, scanner, WebSocket and storefront. Consolidate duplicate API handlers while retaining the intended admin actions. Make alert delivery retryable and reviews product-bound. Then reconcile history schemas and reduce duplicate scanning/ingestion ownership. UI changes should follow truthful data and reliable behavior, not hide missing evidence.
